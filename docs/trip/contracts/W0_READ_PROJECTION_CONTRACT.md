Page strict object `{readVersion:2,actorAccountId,tripId,epoch,revision,accessRevision,pageIndex,records:[{kind,id,revision,body}],pageSha256}`. Relation records have deterministic key string `tableName:<parentUUID>:<childUUID>` rather than fake UUID. Maximum100 pages, total≤10000 roots/64MiB, each page≤4MiB, per-object≤256KiB including bounded child sets; oversize yields COLLECTION_TOO_LARGE and no complete certificate. Never truncate and claim completeness. Hash uses existing canonical ECMAScript sorted-key JSON as bytes, domains `otr-trip-core-object-v2`, `otr-trip-core-page-v2`, `otr-trip-core-manifest-v2`, each followed newline and canonical text excluding its own hash. No pg jsonb::text substitution. Same snapshot/actor/access generation across pages, all roster/count/hash proofs verified before install. Access changed while fetching ⇒ invalidate whole response and retry; pagination token signed/opaque binds manifest,actor,Trip and expires15minutes. Expiration does not destroy already accepted offline snapshot.

v2 schema family/command/field metadata versions are independent from temporal_contract_version1 and existing Person/Ledger/source catalog v1 certificates. v1 wholeTrip UNASSIGNED collection cannot certify actor-filtered v2 absences. Protected pending local intents are overlays, not part of server hash.

## 2. Stable DTO

Root snapshot records use snake_case matrix fields and exact table child names; root required nullable keys are present with NULL, no omission inside hash. Experience adapter returns camelCase finite view below; optional unknown presentation properties are OMITTED, never empty string/zero/fake midnight. This mapping is presentation, not writable data.

`ItemView={itemId,tripId,itemRevision,family,title,status,hidden:boolean,localState:ACCEPTED|PENDING|CONFLICT,participation:{mode,personIds:UUID[],selfPersonId?:UUID,rosterHash?},schedule:{shape,start?:BoundaryView,end?:BoundaryView,origin?:EndpointView,destination?:EndpointView},place?:PlaceView,details?:FamilyDetails,bookingSummaries:BookingSummary[],entitlementSummaries:EntitlementSummary[],documentSummaries:DocumentSummary[],instructionShortcuts:InstructionShortcut[],expenseLinkIds:UUID[],capabilities:ItemCapabilities}`. Arrays contain only visible associations; no inaccessible target pointers. BoundaryView exact optional fields `{localDate,localTime,precision,quality,basis,zoneId,instant,civilResolution}` from accepted tuple; `comparable:boolean` required and true only qualified normalized instant/EXACT or accepted resolved civil. BookingSummary `{id,revision,title,provider?,commercialStatus,confirmationCode?,price?:Money,due?:Money}` only after Booking ACL; no PNR from private Booking on shared Item. ## 3. Day rows and deterministic projection

DayRow strict view `{rowKey:{itemId,projectionRole,localDate},itemRevision,projectionVersion:2,certificateGeneration,family,title,status,position:TNS|TIMELINE|BASE,displayTime?:BoundaryView,place?:PlaceView,itemRef:itemId,visualGroupKey?:string,capabilities:ItemCapabilities}`. No new Event UUID or writable row. Projection roles START,END,CHECKIN,CHECKOUT,BASE_FROM,BASE_RETURN,TONIGHT,PICKUP,RETURN,ORIGIN,DESTINATION,ENTRY; root schedule owns positioning. Row keys persist independently of title/provider enrichment; changing date changes key but Item ID stays stable. No accepted Date→midnight conversion.

- P1/P6: start on authored date, time qualified → Timeline; date-only/unresolved→TNS; optional independently known end on different date gives END, never invented duration. ENTRY place enriches P6 start; no additional Canonical event.
- P2 sparse: ORIGIN row on departure date, TNS with literal and SPARSE. Qualified: ORIGIN and known dated DESTINATION, both independently clickable, existing service attribution retained. Missing destination does not fabricate arrival. Historical service revision loss does not revoke accepted endpoint facts.
- P3: CHECKIN on start date, CHECKOUT on end date; overnight occupancy interval [startDate,endDate). Intermediate dates with other visible activities yield BASE_FROM and BASE_RETURN, no clock; no other activities yield TONIGHT only. A zero-night day-use stay has check-in/out only, no overnight base. Per-person base selection requires exactly one visible applicable Stay for that night; overlapping/unknown/self-hidden arrangements never guessed, ambiguity does not trigger mandatory Review. Group base only if a single shared applicable Stay across roster; otherwise no group-base shortcut. Date-only check-in/out TNS; permitted hours shown separately, never promoted to planned arrival.
- P4: PICKUP on root start, RETURN only if end date known. No middle-day repeated event. Visual grouping ONLY if known identical local date+qualified instant/precision, same accepted place identity (or exactly equal authored operation place without route claim), same PICKUP/RETURN role and compatible visible scope. Same date with unknown clock cannot auto group. Group shell exposes every original Item/card and attachment, not a new root; different returns remain separate. Plate emphasized only if admitted verified/manual plate; category retained.
- P5: each actual leg ORIGIN/DESTINATION independent; no segment collapsed into Booking or guessed Transfer Event. Grouping consecutive visible legs can add neutral interval only if proven comparable destination≤next origin and same relevant clock interpretation; no risk threshold/route judgment or short-transfer auto Review.
- P6: original admission/seat/access enriches existing dated Item; long Pass without Item creates NO Day rows.

Ordering: Timeline by exact normalized instant (microsecond-safe) then order_index then accepted created_at then UUID/role; TNS explicit order_index (NULL last), created_at then UUID/role. Pending addition order uses durable created_at, marked pending; server created_at retained after acceptance. Date/zone presentation from field, not device locale timezone reinterpretation. Root status canceled/skipped/hidden excluded default active Feed; history filter returns authorized rows with status, original association history and no automatic open/active-ticket focus. completed retained in history/today according to existing view selection, not recreated. Sorting and grouping are deterministic adapter functions; accepted projection stores source revision and certificate generation. No feature fetch/provider mutates Day facts.
