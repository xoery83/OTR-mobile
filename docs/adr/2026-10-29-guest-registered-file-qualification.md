# Current Guest registered-file qualification

The approved Guest workspace currently exposes Trip/P1 without file producers.
Photo and Receipt normal copy entrances require a formal Account before copying;
Source confirmed Capture/Documents are Account-only with registered original BLOBs.
Their low-level helpers may write before SQLite registration, so table zero alone
is insufficient and must never establish physical disk absence.

A scoped reader may qualify zero registered business files only for the frozen
schema74 Guest Trip/P1 capability version, with real whole-Guest census/ownership
checks, no unknown nonempty family, empty owning Capture inventory and exclusively
null/registered static cover references. Check legacy and private cover columns,
deferred operations and raw live Trip drafts. Unknown/photo references preserve
original data and block qualification. Future file-producing families/schema or
capability changes require their own updated owning qualification.

Only actual readers produce this internal qualification; caller-supplied COMPLETE
metadata is not proof. No Account directory enumeration/reclassification, file copy,
cleanup, upload, quota or cloud authority follows. Auth checkpoints, caches and
bundled static assets are not transferred business files. General all-family file
inventory and temporary-lease recovery remain outside this limited qualification.

The handoff assembler freezes the existing Guest vault and both actual UI
registries. It verifies canonical draft bytes/Trip/Actor pins through the same
journal verifier, checks live cover references and matches the qualified table
fingerprint to a final real census. Only then does it compute the internal empty
file metadata; it never accepts caller COMPLETE entries. Its return explicitly
has cloudAuthority=false and is limited to the current closed capability domain.

Before publication, UI resume and vault release share the existing Account apply
gate. Once a publish-request is recorded, resume is refused and all locks remain;
only the future server-authoritative receipt/recovery coordinator may complete that
lifecycle. No local success, receipt substitute or protected hold-reset is added.
