## IMPORTANT findings — must fix

### F1: Host networking exposes Caddy administration to Backend code

Locations: `deploy/dev-backend/compose.host.yml:10`; `docs/ops/DEV_BACKEND_RUNBOOK.md:203–204,230–241`; actual host `127.0.0.1:2019`.

**What this is:** The running Caddy administration API uses a host-loopback TCP listener. Caddy and a host-network container share network namespace `net:[4026531840]`. The candidate's HTTP bind restricts incoming Backend connections; it does not restrict Backend access to other host listeners.

**Problem:** Two fresh disposable containers on the exact existing `dev-backend_default` network rejected `127.0.0.1:2019` and host gateway `172.18.0.1:2019` with ECONNREFUSED. A fresh host-network container, UID/GID10001, read-only filesystem, ALL capabilities dropped and no-new-privileges, received **HTTP200** for credential-free `GET http://127.0.0.1:2019/config/`. No credentials were sent; the response body was destroyed without consumption or retention. Existing Caddyfile has no explicit `admin` directive. Earlier default-bridge control also refused the host interface.

This is a demonstrated new administration reachability boundary, not an assertion of current Backend compromise or a new public unauthenticated Backend route. Caddy documents configuration replacement, modification and process shutdown on this administration interface. The supported API authority makes ingress reconfiguration by compromised Backend code a concrete security risk; **no live mutating API request was sent**, so actual writes are inferred from Caddy's documented administration contract, not claimed as an executed exploit. [Caddy administration API](https://caddyserver.com/docs/api).

**Smallest fix:** Before accepting host mode, isolate Caddy administration from Backend. Prefer a permissioned Unix socket kept outside the Backend filesystem/mounts, if compatible with the host's management workflow; disabling the administration endpoint is an alternative requiring an explicit operational decision. Add a disposable host-container denial check for the actual administration endpoint, including retained operator access and unchanged public/upstream behavior. Caddy or host-policy changes need a separately authorized correction scope; this reviewer applied none. Replace the unconditional “No Caddy edit/reload is necessary” assurance with that security prerequisite.

**If skipped:** Backend compromise gains a management path capable of changing public ingress or stopping Caddy, even though Backend itself binds only loopback. HTTP handler Auth checks remain present, but the existing proxy administration isolation is weaker. Treat all newly reachable host-local services as part of the same trust-boundary inventory.

Evidence: `admin.jsonl` contains exact deployed-bridge controls and host-mode positive; `remote.jsonl` independently records Caddy's listener and shared namespace. Caddy recommends permissioned Unix sockets when protecting administration from other server processes. [Caddy administration configuration](https://caddyserver.com/docs/json/admin/).

**What this is:** The host profile supplies `build` but no `image`. The proposed forward command uses `up -d --no-build --pull never`, while rollback explicitly requires an immutable old-image override.

Preserve `--no-build --pull never`; assert the actual started image again afterward. Do not merge the bridge profile into forward startup.
