## 4. Whole-submitted-batch reconciliation

ACCEPTED DIRECTION: `staging → durable submit → understand whole submitted batch → correlate/resolve whole batch → admit safe semantic results`. CURRENT FACT: CP11 accepts one input per transaction; CP12 defines a Batch but no Batch persistence; SQLite49 persists bounded immutable Runs; CP13B correlation applies to the supplied bounded interpretation input. SQLite50 has task manifest pins, not an authoritative intake manifest.

**A user-level Batch coordinator/projection is needed. Reuse the accepted Batch identity and current Runs; do not create another Job business root or scheduler.** One Job is the user projection of one submission Batch. Add More creates another durable Job/Batch; related presentation does not merge their storage identity. Existing immutable Candidate Sets carry Batch/version/coverage; they do not prove all selected inputs were assessed.

PROPOSED IMPLEMENTATION: C0 specifies a minimal persistent input manifest and context/membership handoff, then C2 implements it through repositories. Persist submission identity/ordered item tokens before independently accepting items; atomically bind each successful CP11 result to its manifest disposition in the owning transaction. CP11 lacks an intake replay key today: a crash between blob commit and manifest linkage can otherwise create ungrouped duplicate Capture references. C2 must address that gap by narrow repository composition/idempotent per-item binding; hash dedup alone is not submission replay proof. Failed/unreadable inputs retain explicit dispositions. Interrupted pending items are not silently labeled failed or accepted; unavailable temporary URIs may require reacquisition of those inputs only. Persist safe metadata, not private paths in diagnostics. No giant batch transaction or UI-controlled processing loop.

The **assessment barrier belongs to Platform/Import orchestration before action-plan selection/preparation**, not to the sheet, picker order, queue lease or Event writer. Bind it to exact Batch manifest version/coverage, every admitted input's processed/failed/unsupported/deferred disposition, exact completed Run references and cross-partition correlation assessment. Include declared failures/deferred coverage in the assessment; don't wait forever or mislabel unsupported material as understood. Resolver-pending critical evidence blocks affected safe actions. Publishing R1 for progress while R2 runs is allowed; semantic mutation cannot be authorized from R1 completion alone.

Barrier satisfaction is not READY, permission, consent, global evidence completeness or atomic Batch commit. Domain closure and current pins/CAS remain mandatory at confirmation/dispatch. New evidence means new immutable Run/Candidate Set and predecessor lineage, never append to READY. Whole-batch planning should produce one supported complete Flight action when possible; unsupported PNR/passenger fields remain deferred. Multi-command dependencies use I2 and exact predecessor receipts, never arbitrary parser order.

**Impact:** initial durable manifest/membership requires additive local persistence unless an owner-approved installed store is identified; no server Batch table is proven necessary. Barrier is primarily orchestration plus durable coverage/projection. Exact assessment persistence and any later server contract are UNKNOWN pending C4 preflight; do not assign SQLite51/Server84 here or reuse an adjacent migration number blindly. Platform/Import owns that decision. Staging/intake/read-only progress proceed before barrier completion. Large/slow partial settling is deferred: first bounded Beta must cap/reject unsupported scope explicitly, or withhold semantic admission of a still-unassessed batch. No silent truncation or time-based exception.

Future proofs: permute input order and parser completion order; hold R2 while R1 finishes and assert zero prepared/admitted actions; reverse complementary Flight evidence and obtain equivalent single supported plan; exercise >one Run cross-partition overlap and failure coverage; kill/reopen before/after barrier; stale manifest/pins reject preparation; concurrent Add More invalidates old attention assessment; UNKNOWN predecessor prevents competing CREATE despite a new batch/candidate. Reuse current closure predicates, retained locators/alternatives, evidenced deadline/urgency policy, drafts/reviewed decisions, CP14 task snapshot facts and exact receipt outcomes. They do not define semantic requirement identity, cross-Job dedup, importance, maturity, Not Sure/Later/Skip durability or a production Banner. Ledger Finding/ACK/DISMISS is not this engine.

**Activity-only should precede Banner.** C3 shows Jobs; C6 adds a constrained renderer for supported real requirements, product-owned localized templates and existing typed controls/canonical Forms. Start with the supported Flight question/action surface, not arbitrary generated UI or every conceptual Review kind. If no canonical Form/writer exists, the action is unavailable. C6 requires approved current requirement/version and human-intent contracts; it cannot map Skip mechanically to REJECT or treat dismissal as truth resolution. PROPOSED minimum later presentation handoff, not a DTO/schema: owner scope and capability; Batch/manifest and related Job references; semantic subject/issue reference plus assessment version; current unresolved/actionable/mature state; importance policy/version and separate current urgency/deadline; shown alternatives/evidence permission; decision/reconsideration references; deep-link target; related-intake activity; interaction-cycle/suppression observation.
