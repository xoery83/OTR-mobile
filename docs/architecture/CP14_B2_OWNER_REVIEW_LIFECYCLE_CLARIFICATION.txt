1. PROPOSAL STAGE

After package interpretation / consolidation / closure determines that user
review is required:

- retain the package in the accepted NEEDS_REVIEW state;
- retain/increment the accepted review_version;
- publish only the admitted minimized proposal/reference projection;
- retain Candidate/Run/Input/evidence references through existing accepted
  package/publication-reference mechanisms;
- do NOT call inbound_ai_reserve_review;
- do NOT assert confirmed_user_id;
- do NOT assert confirmed_at;
- do NOT allocate or persist a confirmed Review Decision;
- do NOT allocate Confirmation/output-slot/operation/intended-Event authority
  merely because a proposal is being shown.

A proposal is not consent and is not canonical authority.

2. PROPOSAL IDENTITY

The proposal must still have stable replay identity using the existing package,
review_version and retained publication/reference facts.

Repeated STATUS/proposal retrieval for the same package/review_version must
return the same semantic proposal.

Do not invent a second proposal journal unless existing accepted persistence
proves insufficient.

If exact stable proposal replay genuinely requires new durable authority,
STOP again before adding it.

3. USER DECISION

Only after an actual authenticated OTR user explicitly chooses:

ACCEPT / REJECT / DEFER

may B2 reserve a durable Review Decision.

At that point:

- require verifier-derived OTR_USER;
- require exact current Account;
- require current Trip access;
- require exact package;
- require exact review_version;
- require exact Candidate hash/generation;
- require exact Run/Input/material references;
- require exact Event/base revision where applicable;
- bind confirmation_source = EXPLICIT_USER;
- bind confirmation_scope = EXACT_REVIEW_DECISION.

The External AI client may transport the request but cannot become the
confirming user.

4. GENERATED AUTHORITY IDS

For ACCEPT:

Allocate/retain the exact Confirmation/output-slot/operation/intended-Event IDs
as required by the accepted Server83 + CP13A contract at confirmed decision
reservation time, BEFORE CP13A prepare side effects.

Exact replay of the same authenticated decision returns the same IDs.

Response loss must never allocate a replacement set.

For REJECT / DEFER:

Preserve the accepted Server83 rule that Confirmation/slot/operation/Event IDs
are null.

Do not manufacture canonical authority for nonaccept decisions.

5. CP13A ORDER

The accepted order is therefore:

Package reservation
→ interpretation / N→M / consolidation / augmentation
→ closure
→ NEEDS_REVIEW proposal
→ authenticated explicit OTR user decision
→ durable Review Decision reservation
→ stable generated ACCEPT IDs where applicable
→ CP13A prepare
→ CP13A canonical admission / exact recovery

This ordering is now authoritative for B2.

6. REPLAY

Required replay behavior:

- proposal retrieval loss:
  recover same package + review_version proposal;
- ACCEPT transport loss before/after decision reservation:
  recover exact retained Review Decision and generated IDs;
- REJECT/DEFER transport loss:
  recover exact retained nonaccept decision;
- CP13A prepare response loss:
  recover exact retained preparation;
- canonical response loss:
  use CP13A exact recovery.

Never create a replacement Review Decision because a transport response was
lost.

7. STALE PROPOSAL

If, between proposal display and user decision:

- review_version changes;
- Candidate generation/hash changes;
- Run/Input/material identity changes;
- Event/base revision changes;
- Trip access changes;
- grant/client transport authority changes where relevant;

the old proposal cannot be accepted as current.

Return the admitted stale/review-refresh disposition.

Do not silently apply the old proposal to new truth.

8. EXTERNAL CLIENT ROLE

External client may:
- submit package;
- retrieve authorized minimized status/proposal;
- transport an authenticated user's decision request where the trusted host
  context proves the OTR user.

External client alone may NOT:
- reserve an ACCEPT decision as itself;
- set confirmed_user_id;
- set confirmed_at;
- claim EXPLICIT_USER confirmation;
- allocate canonical authority IDs;
- bypass OTR user authentication.
