## Exact handoff and missing guarantees

1. **Staging→CP11 adapter.** C1 exposes `CaptureSelection`/`StagedCaptureItem` in `src/features/capture/captureStaging.ts`; native acquisition is `src/native/capturePicker.ts`. There is currently **no submission adapter**. The prospective owning operation must turn a readable temporary reference into `CapturePayloadInput.reader` and valid `CaptureMetadata`, then use `getDefaultLocalCaptureInboxRepository().intake(metadata, input)` from `src/data/repositories/defaultLocalCaptureInboxRepository.ts`. `src/data/repositories/localCaptureInboxRepository.ts::intake` owns context, bounded reading/hash, quotas, BLOB/reference transaction and acknowledgement. Files map to FILE; Photos-origin images can map to IMAGE under the future admitted intake contract. Neither acquisition origin nor CP11 kind is semantic role/classification. Do not route ordinary Media to Documents by file format.
2. **Metadata at submission.** Files: URI/name and optional declared MIME/size. Photos: URI and nullable filename/MIME, optional size, width/height. C1 keeps source, session-only numeric staging ID and unverified/unavailable status. It intentionally drops EXIF/base64/provider bodies; URI is never displayed/logged. Camera is not implemented; it has no C1 submission reference. OS-native picker cache/export behavior does not establish original format/fidelity. No real selected URI lifetime was tested.
3. **Temporary-reference lifetime.** Files disables `copyToCacheDirectory`; some provider/security-scoped/content URIs may not be immediately readable through Expo File APIs or may expire. Photos may produce an OS/plugin temporary export. C2 needs actual per-platform/provider acquisition probes and, where required, a native accessible bounded reader/copy bridge before the handle expires. Do not promise that reconnect/restaging can recover disappeared bytes. Retain immutable bytes through CP11 before claiming acceptance; no receipt normalization/compression or unconditional full-byte read. `capturePayloadReader.ts` requests at most 64 KiB per read and enforces 10 MiB binary/1 MiB text. Reader.close runs on failure. Size hints are not integrity proof.
4. **One submission identity.** Reserve one durable Account-owned user submission/Batch identity and immutable invocation context before item acceptance; Job projects that identity, not one continuation task or Run. Persist stable ordered item references and replay identity. Add-more after a submitted batch creates an independently durable intent as approved, without a second scheduler. C0 must settle the exact cross-owner identity and count contract; no C1 staging ID may masquerade as that durable identity.
5. **BLOB→manifest crash window.** CP11 atomically writes BLOB plus Capture reference, but it cannot currently atomically link that Capture to a Batch item. Calling `intake` then persisting linkage leaves a kill/lost-ACK window: original retained, manifest still pending, caller lacks acknowledged Capture ID. A second intake can create another reference. A future approved repository transaction must bind stable item replay key, exact retained Capture identity and accepted membership at the same commit boundary; do not repair by scanning filenames/hashes or weakening immutable guards. Account gate alone is serialization, not crash durability. Do not call the existing nested-transaction intake from an outer transaction unchanged.
6. **Missing idempotency.** `intake(metadata,input)` accepts no submission/item/replay key and allocates `newId()` after read/hash. Stable identity is not known to the caller before a lost acknowledgement. Exact-byte dedup is insufficient for reference replay. C0 must approve the smallest repository-level idempotent item admission/link contract, immutable request binding and exact replay/recovery behavior. This report adds none.
7. **Truthful item states.** Future durable projection distinguishes pending (not yet accepted), accepted (verified committed CP11 binding), failed (known unsuccessful intake with safe reason) and needs reacquisition (bytes/reference unavailable). Unknown commit outcome must retain pending recovery responsibility, never become failure or a new item/key. These are required meanings, not a production enum/schema proposal. Semantic processing/READY/prepared/admitted results remain a separate axis; accepted bytes do not imply plans added.
8. **Existing store coverage.** SQLite48 `local_capture_payloads`/`local_capture_inbox` persists independent immutable originals/INBOX or ASSIGNED references. SQLite49 Source bindings/catalogs persist explicit admitted Source/Run/Input relationships, not all submitted selections or partial failures. SQLite50 `intelligence_continuations` retains immutable `import_id`, manifest version/hash and task/attempt facts; `snapshot()` reads a task and attempts, not durable Batch membership. No inspected store provides complete user-submission manifest, historical invocation snapshot and per-item replay. The default continuation composition remains unwired.
9. **Minimal persistence invariants if approved.** An additive local manifest appears necessary: Account-scoped stable submission/item identities; immutable original invocation context and ordered membership; exact replay/request binding; accepted item→Capture linkage in one transaction; monotonic per-item disposition/revision under CAS; partial recovery without duplicate references; retention of linked originals and unresolved responsibility; repository checks equivalent with FK OFF. No migration number, schema body or server change is assigned. Historical SQLite1–50/server1–83 remain untouched.
10. **Historical Account/Trip context.** C1's host admits a real local Account and fixes invocation prior; it does not persist context or pass root-selected Trip. C2 must capture the authenticated Account plus explicit nullable Trip/context snapshot under a fresh existing request generation, persist it once and revalidate current permission during acceptance/recovery. Trip prior is separate from resolved assignment; blindly passing it as CP11 `tripId` would prematurely ASSIGN. Account change cannot rebind old intent. Fresh A may recover A's durable submission after A→B→A; old generation callbacks cannot.
11. **Partial success / kill.** On reopen, project the same retained submission and each committed accepted binding. Unaccepted items need exact replay or reacquisition, without claiming all selected references were saved. An accepted original can remain accepted even when another input exceeds quota or disappears. No new Job/key may be generated merely because the UI remounts. UI dismissal never deletes durable evidence or unresolved operations.
12. **Duplicate bytes versus references.** CP11 verifies Account-local hash/size candidates against exact bytes before payload reuse. Each new logical intake still creates a Capture reference. Re-selecting the same bytes can represent independent submitted intent; replay of the same submission item must return the same retained binding. Global byte dedup, hash-as-entity-ID and semantic duplicate matching remain out of scope.
