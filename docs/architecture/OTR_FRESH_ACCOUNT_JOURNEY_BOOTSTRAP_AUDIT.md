## Account safety finding that must accompany composition

Current refreshMyLedger fetches with myLedger(), then cacheMyLedger resolves the active user at apply time. Neither carries a captured Account/generation through the response and transaction. A response requested as A can finish after switching to B and be stored as B; an old A response can also survive A→B→A. The MyLedgerScreen generation check occurs after cache apply, so it only protects rendered callbacks, not stored rows. This is a confirmed code-path hazard; no live cross-Account race was exercised.

Fix that shared boundary before reusing discovery. Capture immutable Account ID/generation before token acquisition; check before dispatch, after await, and inside withAccountApplyGate plus the SQLite transaction. Bind writes to the captured ID rather than a newly resolved active user. Reuse existing context validators; a narrow Account-only context type derived from the current context is sufficient. Do not invent a fake Trip ID or treat summary data as membership capability. Keep existing Trip-specific context checks unchanged.

Likewise, new automatic selected-Journey writes and list/projection callbacks must be generation-fenced. Ledger loadContext currently awaits list/selection before assigning setJourneys; add a current Account/generation check to discovery-driven reloads. Preserve existing My Ledger view-generation masking, Account transition clearing and certified bootstrap gates. A definitive current 403 must prevent new hydration; discovery-list absence alone cannot establish revocation because this is Ledger eligibility, not a universal admission certificate. Never delete user-owned rows/queues in response to absence or transient failure.
