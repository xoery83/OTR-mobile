# Device Storage Management 1.0 — Phase 3A audit and design

Date: 2026-09-27. Status: **Phase 3A audit complete; bounded Phase 3B safety gate implemented**. This is OTR-wide infrastructure. The first implementation integrates only the existing receipt/Expense attachment and Personal Payment evidence paths. Trip attachments and Album media have no current local lifecycle to register. Album original ownership, retention, quota, download ownership, and pricing remain undecided for Album product design. Cloud usage is Phase 4.

## Scope and evidence

This is a source and approved-device-evidence audit, not a live sandbox inventory. No device, Hosted Dev, object, or Production file was inspected or changed. Source anchors: `src/data/files/receiptFileStore.ts`, `src/data/operations/{expenseReceiptDraft,importReceiptAsset,openReceiptAsset,ledgerMaintenance}.ts`, `src/data/repositories/ledgerReceiptRepository.ts`, `src/data/sync/{ledgerReceiptSyncWorker,ledgerReceiptTransport,ledgerOperationalSync}.ts`, `backend/src/{attachmentStorageProvider,supabaseGateway}.ts`, `src/data/db/{database,migrations}.ts`, and the accepted attachment Phase 1/2 plans. The actual backup flags, data-protection class, disk use, and orphan counts on each installed device require later device verification.

## Orphan and missing-file risks

1. Picker/native temporary output after cancel, thrown validation, crash, or successful copy can be left behind. A picker-owned cache copy is normally **definitely safe garbage only after OTR has a separately verified durable copy or explicit cancellation**; do not sweep foreign Photos/iCloud paths.
2. `createTemporaryReceiptDraft` copies bytes before JSON; failure/crash can leave an unrecorded draft. Existing Expense/Personal Payment deliberately do not write JSON. These are **potentially recoverable user data** until a matching committed asset or explicit abandonment is proved. Invalid draft JSON/bytes are **cannot determine safely**; recovery deliberately retains them.
3. Preparation creates `ledger-receipts/<id>` before the SQLite transaction. Rejected/rolled-back Save/import leaves no row and perhaps a still-valid draft source. The prepared copy is **potentially recoverable** until the source/transaction outcome is known; after a matching committed asset and verified source it is safe to remove only the redundant WORKING source. No blanket unreferenced-file sweep.
4. Post-commit draft deletion may fail or crash, leaving bytes/JSON: **definitely safe duplicate only after** matching asset local file hash and committed upload operation are verified. `restoreExpenseReceiptDrafts` filters committed IDs but does not delete duplicates.
5. Tombstoning/unlinking does not remove local receipt bytes; completed operation pruning can erase convenient evidence. These are **cannot determine safely** until canonical tombstone, no payment link, no pending operation, and recovery window are checked. Remote objects also remain but are outside local GC.
6. Existing `enforceReceiptCacheLimit` deletes the file before setting `local_uri = NULL`; a crash/SQL failure leaves a row with a missing path. `resolveReceiptFile` fallback may also mask a stale container URI. Classification: **recoverable only if current authorized remote bytes still match**; otherwise potential data loss. It should check current references and operations immediately before deletion.
7. iOS can purge Cache downloads and Expo temporary inputs. Their missing paths are expected **only if** no durable local asset depends on them. Documents may also be missing after external corruption, failed copy, user uninstall/restore, or a previous eviction; a PENDING/FAILED missing receipt is a **user-data recovery incident**, not garbage. No startup scan currently reconciles this.

## Remote durability and CACHE eligibility

`PUT` verifies client bytes against `receipt_assets.size_bytes/sha256`, calls provider `put`, then records `uploaded_size_bytes/uploaded_sha256`. `completeReceipt` checks the client's object key/size/hash against those DB fields and sets `upload_status=UPLOADED`; it does **not** call `stat`. `storage_provider` and `object_path` identify the object in Postgres; Mobile DTO/local SQLite has object path but no provider field. Phase 2A `stat()` currently **downloads the Supabase object and hashes actual bytes**, returning byte count, blob content type, and SHA-256; it is capable of an independent exact-byte check, though it reads the whole object into Backend memory. MIME from the downloaded blob is a useful check but must be validated against stored MIME; ETag is not SHA-256. A `stat` result proves observed bytes at that moment, not perpetual availability or backup policy.

Minimum transition: keep all existing files PROTECTED by default. In a later Backend slice, after `put` (including idempotent completion replay), resolve the row's provider/key and require `stat` exists with exact stored byte count, SHA-256, and acceptable content type. Record a server-owned confirmation tied to **provider + object key + expected SHA + size + version/time**; never accept a client claim as that confirmation. Expose only a constrained confirmation state to Mobile and persist it locally. A local copy becomes CACHE-eligible only while the receipt is active, upload and relevant link/deletion operations are settled, the local file is known to match the confirmed representation, the authenticated download route is permitted, and no other local-only role requires it. Recheck membership/tombstone/queue state before eviction. A failed stat/download, stale confirmation after overwrite/provider change, unknown provider, or changed hash returns it to PROTECTED. For the first migration, existing UPLOADED rows remain PROTECTED until independently confirmed; a one-time device-local fresh authenticated download matching bytes can also serve as conservative proof for the **specific eviction**, but should not silently relabel other rows.

**Existing safety gap and sequencing:** `runLedgerOperationalSync` already calls `enforceReceiptCacheLimit(database, 250 MiB)` after each operational cycle. This old function downloads and hashes each candidate immediately before deleting, so it does not rely solely on UPLOADED. It nevertheless mixes protected+cache sizes in its budget, lacks a durable cache class, does not account for its Cache downloads, and deletes before clearing the DB URI. Phase 3's first coding slice must gate/replace this path before broader eviction is enabled. It must not be treated as evidence that Phase 3 is already implemented.

## Redownload and measurement

Backend `GET /v2/trips/:journeyId/receipts/:id/content` is authenticated, checks Expense/Personal Payment read rights, rejects tombstones and non-UPLOADED rows, then provider-reads bytes. Mobile `openReceiptAsset` downloads the whole response into memory, checks expected size/SHA, writes `Paths.cache/<server-id>.<ext>`, and opens the share sheet. It does **not** persist the Cache path, find it on the next open, or update `local_uri`. A removed Documents copy can be reopened **online today** if still authorized and remote is intact; offline reopening does not work. Needed: own deterministic Cache directory, validate any existing cached file before use, atomically write and verify a new one, and record or derive its path without making OS-purgeable bytes look durable. Share only after verified write; handle Cache purge, auth failure, tombstone, and interrupted writes. Do not write `local_uri` to an OS-purgeable path unless all upload/recovery logic distinguishes it from protected originals.

For accounting, use SQLite `size_bytes` only as expected representation and enumerate **known managed roots** for actual physical size (receipt originals, draft bytes/JSON, owned Cache, exports, DB). `File.size`/`Directory.size` can verify known paths, and `Paths.availableDiskSpace` can report device-wide free space; neither is an OTR total. Avoid full sandbox walks and summing metadata for missing files. The old maintenance sums row sizes including PROTECTED, ignores unreferenced download Cache, and uses `updated_at` as an eviction order even though updates can be sync events. No `last_opened_at` or `last_downloaded_at` exists. `created_at`, Journey start/end dates, and server update time exist; active/upcoming/past is derivable from Journey dates but not a storage priority contract. V1 can use verified cache creation/last download time or receipt creation time, with active/upcoming Journey bias only if product agrees; no full LRU field until simple age proves inadequate. Include account and domain ownership in any cache registry.

## Conservative management design

Lifecycle classes are **PROTECTED**, **WORKING**, **CACHE**, based on recoverability rather than feature or current directory. These are conceptual until a migration supplies durable proof. The manager handles known local objects, not Expense or Album rules. An integrated domain supplies a small snapshot/adapter: stable local ID and owned path, account/domain, class, actual bytes, age/order, eligibility with evidence reference, and a domain method that atomically checks current state before removal. Avoid a generic plugin framework or global sandbox crawler. Future Trip/Album domains can register only after their own lifecycle and redownload contract are approved.

WORKING GC uses positive evidence: successful committed destination+matching hash, explicit cancel with a known draft ID, confirmed obsolete version, or confirmed tombstone with no remaining link/operation and an approved recovery window. Check canonical path is under an OTR-owned root; recheck same ID/owner/hash/current references and operations immediately before deletion. Unknown/ambiguous artifacts go to diagnostics/manual review, not deletion. Run bounded post-operation cleanup and occasional startup/foreground maintenance; no continuous scan. Preserve interrupted transactions and account switches. No deletion of app-external picker sources.

CACHE eviction accepts only independently remote-confirmed, re-downloadable, active objects with no pending/failed operation or protected use; it must never delete cloud objects, SQLite domain rows, settlement exports, or PROTECTED/WORKING files. After a fresh state check, delete the exact owned path idempotently, then mark local cache absent; a crash between steps must be recoverable by observing file existence on restart. A write should use a temporary sibling and atomic move where supported; partial files are never registered as CACHE. Clear Cache calls the same eligibility/removal path, applies no budget, and reports only verified reclaimed bytes. Offline Clear Cache can act only on previously confirmed CACHE with still-valid local evidence; if confirmation freshness/permission cannot be established, retain it. No file should be promoted by `UPLOADED` alone.

The proposed **500 MiB** is a global _disposable cache_ design baseline, not an app/device cap. Phase 1 synthetic prepared receipts were ~0.39 MiB JPEG/HEIC and ~5.83 MiB transparent PNG; each new receipt is at most 15 MiB, so 500 MiB could hold hundreds of typical receipts or tens of worst-case ones, but Album size/frequency and real-device distributions are unknown. Current 250 MiB automatic receipt limit is not equivalent and must be reconciled deliberately. Tentative hysteresis: start at 500 MiB, trim to ~400 MiB, with free-space pressure allowed to request earlier trimming of CACHE only. Defer a user-configurable budget and final value until device measurements; protected bytes may exceed 500 MiB.

## Settings and protected-storage UX

First Settings > Storage: **On this device** = measured OTR-managed local data (protected files + working files + cached files + DB + retained exports, with a clear “approximate” qualifier if any known root cannot be measured); **Cached files** = currently present, verified disposable managed bytes; **Clear Cache** and text: “Removes files that can be downloaded again. Your trips, expenses and cloud files won't be deleted.” Do not call the entire iOS app footprint “On this device” without accounting for app binary, Expo/native caches, and unknown OS-managed files. If scope is only managed data, label it accordingly. Cloud storage usage waits for Phase 4. No permanent LOCAL_ONLY/PENDING breakdown in normal UI.

Show actionable protected-storage messaging only after a sustained upload backlog becomes material, for example unuploaded protected bytes >1 GiB **and** uploads blocked/failed for 24 hours, or low free disk plus a blocked backlog. These are evaluation thresholds, not approved product constants. Message “Files waiting to upload — 1.2 GB” with a retry/connectivity action, never a Clear Cache suggestion for those bytes. Check real-device usage before selecting thresholds.

## Migration and acceptance gates

Likely additive Backend/Postgres confirmation fields (or narrow confirmation record) and DTO version; additive SQLite confirmation/managed-cache metadata and perhaps a single cache timestamp. No total-storage limit field. Existing local URI and receipt objects remain until verified recovery. Moving old uploaded copies from Documents to Cache is optional and deferred until per-file confirmation; leave protected originals in Documents. New confirmed copies should live in Cache, WORKING in an owned temp/working root with a recovery window, and PROTECTED in persistent app storage with verified backup policy. A protected draft in OS-purgeable Cache is unsafe. An Expo-only app may need a small native/config change to exclude reproducible Documents copies from backup or use Application Support; verify SDK/native capability before promising it. Do not change file protection without an offline/restart device test. Production migration/deploy is not part of Phase 3A.

Test strategy: one safety-focused suite for protected PENDING/FAILED/unknown-provider never evicted; stat mismatch/404 and idempotent replay; successful confirmation; Clear Cache leaves WORKING/PROTECTED and cloud/DB intact; interrupted delete-before-DB-update and partial download; budget hysteresis/order/free-space pressure; GC positive evidence versus ambiguous orphan; authenticated re-download/open, offline miss, cache purge, restart/container-path rebase; tombstone and Personal Payment link/unlink; account isolation; future domain adapter contract with a fake Trip object. Physical iOS acceptance: offline restart with LOCAL_ONLY, online confirmation, low-storage behavior, OS-purged Cache, Settings byte totals, and backup/file-protection spot checks. Use synthetic media only.

## Proposed coding slices and checkpoints

### Phase 3B bounded safety decision

Keep the legacy 250 MiB receipt threshold. For each candidate, require an authenticated Backend HEAD of the existing content route that resolves the canonical provider/key and calls provider `stat()`, followed immediately by the existing authenticated GET and Mobile size/SHA check. Recheck local row and operation state before clearing its URI and deleting the exact owned file. Because this proof is obtained afresh for **each** eviction, do not persist a reusable remote-confirmation flag or add schema in 3B: there is no old confirmation that could survive a provider/key/size/SHA change. A failed or changed HEAD/GET leaves the file protected. This HEAD contract is for receipt eviction only, not the future storage manager.

After this slice, stop Device Storage work. Phase 3C and later slices are temporarily deferred; the next product-development area is Receipt OCR 1.0. No global budget or reusable download cache is included.

1. **3B0 safety gate (first):** inventory/freeze the existing 250 MiB automatic receipt path; ensure no automatic removal can run outside the eventual CACHE eligibility gate. Preserve the current verified-recovery behavior or temporarily disable eviction while the confirmation path is built. Regression test protects PENDING/FAILED/Personal Payment and interrupted deletion.
2. **3B remote durability:** Backend provider `stat` confirmation after put/replay, persisted provider/key/hash/size evidence; Mobile DTO/local additive confirmation state. Old rows default unconfirmed. No local deletion yet.
3. **3C redownloadable cache:** owned Cache path, verified atomic download/reuse, missing-file/restart/offline behavior; no budget yet.
4. **3D Working GC:** positive-evidence cleanup for draft/prepared/obsolete artifacts, bounded triggers, diagnostics for ambiguous files.
5. **3E global budget:** small domain registration contract, actual-byte accounting, 500/400 MiB candidate hysteresis, safe eviction and crash recovery. Integrate existing receipt and Personal Payment evidence only.
6. **3F Settings/acceptance:** measured Storage summary, Clear Cache on same safe path, actionable protected backlog messaging only after threshold evidence, iOS device acceptance.

## Phase 3B implementation and acceptance (2026-09-27)

- The existing `runLedgerOperationalSync` trigger and **250 MiB receipt-specific threshold** remain. The old query considered every asset row with `local_uri`, summed expected `size_bytes`, and ordered by `updated_at`. It selected an UPLOADED row with `server_id`, downloaded through the authenticated Backend GET, checked byte count/SHA, deleted the local file, then set `local_uri = NULL`. Protected bytes counted toward the threshold but were not deleted unless status and recovery checks passed. This is transitional behavior, not the planned global cache budget.
- The new safety gate additionally requires an active, non-tombstoned row; canonical object key; known receipt MIME; exact OTR-owned Documents receipt path; intact local file; no non-completed asset operation; and a successful authenticated HEAD. Backend HEAD uses the same read authorization as GET, resolves the canonical provider/key, calls provider `stat()`, and requires exact byte count, SHA-256, and MIME. Mobile compares HEAD's key/size/hash/MIME with its local snapshot, then still downloads through authenticated GET and independently checks byte count/SHA. Unknown provider, inaccessible/missing/mismatched object, pending upload/link/delete (including Personal Payment), LOCAL_ONLY/FAILED, draft/working path, and tombstone all fail closed. HEAD/GET alter no cloud object or domain row.
- No schema or persistent confirmation was added: **every** candidate receives a fresh provider stat and actual authenticated download immediately before eviction. Backend/local identity or integrity changes cannot reuse a stale confirmation. The conditional SQLite update rechecks key/size/hash/MIME/status/tombstone/operation state and sets `local_uri = NULL` **before** deleting the exact owned file. An interruption leaves a harmless remote-backed duplicate; it cannot leave a newly deleted file behind a non-null path. Older stale paths remain recoverable through `openReceiptAsset`'s missing-file GET path. Online redownload is size/SHA checked; network failure now explicitly asks the user to reconnect. Reusable Cache copies remain deferred.
- Focused automated coverage passed: 11 files / 102 tests for maintenance, receipt file/repository/sync, Personal Payment, provider, and Backend routing; TypeScript and Backend bundle build passed. A read-only Hosted Dev synthetic receipt check passed authenticated HEAD and GET with exact object key, MIME, byte count (68 B), and SHA-256. Hosted Dev Backend image `sha256:5106284653b9d45993778dbdf236162cead819b6cf3bf100d7bed4762f0bc28f` is healthy; prior source snapshot is retained. No Postgres/SQLite migration, Storage mutation, historical orphan deletion, or Production access occurred.
- Physical iPhone acceptance could not run: `xcrun devicectl list devices` twice timed out while initializing CoreDeviceService. Automated online reopen/offline failure and interruption tests passed, but an actual device eviction/reopen cycle remains unverified. Do not interpret this as a device pass.
- Remaining transitional limits: the 250 MiB calculation still includes protected row sizes and not unmanaged Cache duplicates; stat and GET each transfer the object, so eviction can consume bandwidth. A failed post-DB file delete can leave a safe but untracked duplicate until future working-file cleanup. No global budget or general GC was added.

**Scheduling:** Phase 3B stops here. Phase 3C+ is temporarily deferred. The next product-development area is Receipt OCR 1.0; this document does not authorize its implementation.
