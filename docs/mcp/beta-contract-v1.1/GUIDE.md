# OTR MCP Beta Guide

Version: `otr.mcp-beta.guide/1.1.0`. Owner-approved LIVE Layer3 risk authorization delta over unchanged frozen contract1.0 business schemas. Historical Layer2 planning artifacts remain PLAN_ONLY.

## OPERATING

Private execution context delta `otr.mcp-beta.plan-enforcement/1.1.1`: attach the complete concrete `executionPlan` to every write in a multi-step plan. It is context, never approval; current call and operation must exactly match one actual APPLY step. The server binds a supplied plan to Preview and rejects high-risk multi-step execution before dispatch. A declared ten-target destructive plan establishes restrictive fifteen-minute target fences across clients, operation replacements and omitted context. Classification remains read-only. No approved bulk executor exists; stop at NEEDS_CONFIRMATION, never split/re-key the plan to continue. Single-call normal paths retain their existing rules.

Use the connected OTR Layer3 runtime for actual authorized reads and writes. Read these modules and the selected capability schema first. L1/L2 writes use current OAuth write scope plus formal ACL, server validation and CAS; no per-operation approval click is required. Read the current object, construct only the requested changes, obtain exact PREVIEW, then APPLY that same concrete call/digest/operation. Explain important L2 effects before execution; a warning is not a credential. L3 still requires trusted exact-operation approval. Never manufacture approval or receipts, upload originals, execute unsupported domains or retry UNKNOWN writes. The server's risk registry and actual typed effects are authoritative; never choose or lower risk yourself. A frozen PLAN_ONLY output remains a plan; an actual tool result/owning Receipt is execution evidence. For concrete multi-step planning use get_otr_capability_schema's risk-plan1.1 schema; the legacy1.0 validator still retains its historical all-CONFIRM structure. No plan itself executes or grants authority.

Trip is the travel container with structured destinations, dates, metadataRevision and lifecycle. Item is one canonical plan/occurrence: P1 general plan, P2 flight segment, P3 stay, P4 rental, P5 non-flight transport, P6 activity. Expense is a separate financial aggregate. Booking, Ticket, Source, Instruction, Person, Account and Ledger Member are separate identities/authorities. An Item proves no booking or payment. Evidence does not grant Source/Import authority.

First discover the authorized Trip, current capability facts, relevant complete pages, full ItemSnapshots, Expenses and Roster. Exact user Trip IDs still need a current get. Missing snapshots are not empty results. Stage downstream edits WAITING_RESULT with typed references. Ask a focused selection question for ambiguous Trips/people. Supported capability, runtime implementation and current object permission are different facts. Preserve all 103 contracted abilities even when runtime is unavailable; block only the affected execution branch.

Manual authored data uses MANUAL admission. Do not set actor/role/account in requests. Current Backend ACL/CAS is final. Organizer cannot automatically manage another person's PRIVATE or non-WHOLE_GROUP Item. Visibility controls access; Participation identifies participants and does not share or connect Accounts. Recommended PRIVATE/SELF needs explicit preview and lawful actor Person binding; never invent that binding.
