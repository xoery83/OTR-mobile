# Currency / FX Phase E — provenance and exception UX

Status: source implemented; device acceptance pending. No Production change or Phase F.

## Product language and read model

The Expense detail shows original Money and Journey value first. Cross-currency accepted reference evidence is labelled **Reference rate / 参考汇率**, never actual/bank/transaction rate. `MANUAL_AGREED` is **Agreed rate / 约定汇率** and `ACTUAL_PAYER_COST` is **Actual payer cost / 实际付款金额**. Same-currency Expenses show the identity Journey amount without an FX policy. Missing economic date requests date confirmation; a known date without accepted valuation says the reference rate is pending. A locally queued valuation is explicitly pending sync.

Rate details discloses the canonical original→Journey rate, both dates when available, reason and the accepted reference provenance already cached in the existing SQLite valuation snapshot. When dates differ, the Expense date and actual ECB reference publication date are separate. The European Central Bank is the financial reference source; Frankfurter delivers that source's data. The detail clarifies that this is valuation information, not card/bank cost. No internal IDs or provider payloads appear. A short list of previously cached inactive valuation snapshots explains currency/policy supersession without creating a parallel history store; a newly bootstrapped device does not currently fetch old snapshots, so this is explicitly labelled “on this device.” The canonical server retains all historical rows. No schema or Backend read-contract migration was made.

## Explicit policy changes

Only the linked creator or owner can change an Expense valuation under the Stage 5 server RPC. The broader actor capability flag is not sufficient for another group member. Owner changes to another creator's Expense require a reason at the server; reference restoration supplies one. Detail controls are suppressed for conflict, deleted/pending Expense, and an Expense included in locally cached finalized settlement inputs; the server repeats the revision, membership, quote, posted-payment and finalized-input guards. Other authorized members may read provenance. If local finalized inputs have not yet been pulled, the server remains authoritative and rejects the change.

Agreed rate accepts a positive exact decimal in one direction (`1 original = X Journey`) and a mandatory reason. It previews the exact integer-minor-unit Journey Money using the existing domain valuation function before explicit confirmation. Actual payer cost offers only non-superseded posted PaymentRecords in Journey Currency/scale, previews the posted amount, and explicitly confirms; it never derives a reusable market rate. A synced eligible ECB candidate allows an explicit preview and return to Reference rate. No quote refresh switches an accepted valuation by itself. All three actions use the existing local-first `LEDGER_APPLY_VALUATION` operation, revision/audit and immutable superseding Stage 5 path. The worker maps local payer evidence ID to its canonical server ID and waits until that evidence syncs. Pending operations are not represented as remotely accepted.

Current reports and Review are unchanged consumers of the one active canonical valuation. Stage 5 writes one revised active snapshot and settlement splits, retaining previous evidence; Review re-evaluation follows canonical sync, and settlement readiness reads the active value. Finalized inputs remain frozen. Cached provenance and prior local evidence remain readable without network. The standalone Exchange Rates placeholder is hidden from ordinary Settings navigation; no rate-cache administration is exposed. The route remains inert for old deep links.
