## Current UI and target information architecture

The existing Review route lists all visible Findings together, including historical and personally reviewed items. Its generic cards show live Expense titles and rule prose, not immutable observation evidence. List and detail each own a hook instance; acting in detail does not invalidate the list. Ledger's attention banner counts both OPEN and ACKNOWLEDGED. The selected decision is disabled but a rapid opposite tap can still race.

Review becomes a financial attention inbox: a total personal pending headline; horizontal All, Amount, Duplicate, Exchange rate, Participants, Evidence chips with _pending_ counts; OPEN with only visible active v2 heuristic NEEDS_REVIEW items; a secondary `Reviewed N` accordion, collapsed on entry, containing only active personal ACKNOWLEDGED/DISMISSED items. All remains visible; zero-pending categories are hidden, and a selected category that reaches zero falls back to All. Both lists obey the selected category; the headline and chip counts do not. Resolved, superseded, deterministic, and v1 items stay out of this active inbox. Existing Ledger Review navigation remains available at zero pending; a minimal history affordance may show eligible inactive rows separately, never inside OPEN/Reviewed. Future USER_REQUEST is an extension, not a button/schema in this phase.

## Presentation and interactions

Cards: category, human title, immutable Expense title/date and useful payer where available, one-line rule-specific numerical or identity evidence, personal status in Reviewed, chevron. Stable Finding ID keys and virtualized list rendering; parse evidence once in the repository. Never expose rule IDs/versions or invent market-rate/OCR comparisons.

Detail uses the saved observation context, not today's mutable Expense values:

| Category      | Observation and comparison                                                                                 | Next step                                   |
| ------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| Amount        | Original amount, same-currency/scale Journey median, cohort size, multiplier                               | Open affected Expense                       |
| Duplicate     | Both saved Expense titles, dates, payer identities and amounts; matched Expense ID                         | Open either Expense                         |
| Exchange rate | Recorded rate, source/currency pair when known, actual bound `> 0` and `<= 1,000`, direction               | Open affected Expense; no market-rate claim |
| Evidence      | Original amount, selected posted payment amount and absolute difference; payment record/date only if saved | Open affected Expense; not receipt OCR      |
| Participants  | Payer and saved participant names (fallback to identities if unavailable), neutral explanation             | Open affected Expense                       |

Active eligible detail offers Acknowledge and Dismiss without required reason or confirmation. A local transaction persists personal decision and one durable operation before UI reports success; disable both controls during submission and the selected control thereafter. The Reviewed detail shows personal status, and existing supported change-decision action may remain. The UI says a queued action is waiting to sync, never blocks offline. A later server projection may remove an ineligible, resolved, or superseded Finding; a new generation has its own pending identity.

## Reactive state, counts and navigation

One user-scoped repository projection supplies the active inbox and canonical counts. Notify interested screens after local decision, projection replacement, and invalidation; reload on navigation focus as a safety net for Expense edits/account switches. The Ledger banner uses repository pending count and disappears at zero with no reserved space or `Review 0`. Account identity is rechecked by the repository on every read. The list/detail reload on focus rather than depending on remount. Remote refresh follows immediate cached load; failure retains cache and displays a subtle offline/error message. No full-screen spinner when cache exists. Initial cache absence gets lightweight loading; zero pending says “Nothing needs review,” while Reviewed remains reachable.
