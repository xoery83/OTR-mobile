# OTR Mobile 2.0 Currency & FX Domain Audit (read-only)

Date: 2026-09-17. Scope: this checkout's Mobile code/SQLite migrations, Backend, committed Supabase Dev migrations/functions, Ledger 2.0, Review 2.0, reporting, settlement and UI. No live Dev database query, device execution, Production access, or legacy Web re-audit was performed. “Exists” below means implemented in this checkout, not that a live provider or UI path was proven operational. Current SQLite schema is v21 per `docs/CURRENT_IMPLEMENTATION_STATE.md`. This document is an audit and proposal, **not approval to implement or migrate**.

## Executive finding

The canonical Expense already separates merchant Money, payer PaymentRecord, and accepted Journey settlement valuation. The visual picker is not a conversion tool. Expense selection edits a draft, clears the numeric amount, and only persists after a valid Save. Ledger Settings selection _does_ persist, but only as per-account local `default_currency`; it changes no Journey settings, valuation or report. There is no ordinary UI command for changing Journey settlement currency, and the Exchange Rates screen is explicitly unavailable. Preserving the existing financial evidence model is more important than making a picker appear to recalculate all historic amounts.

## 1. Transaction currency

- Canonical Ledger 2.0 `Money` is `{minor, currency, scale}`; `ledger_expenses.original_amount_minor/original_currency/original_scale` and Dev `expenses.original_*` hold the merchant fact (`src/domain/ledger/types.ts`, `src/data/db/migrations.ts` migration 5, `supabase/migrations/20260911000100_ledger_2_domain.sql`). Stage 2A `expenses.amount_minor/currency_code` is a separate compatibility model, not the active Ledger 2.0 aggregate.
- New/edit Save runs `LedgerExpenseRepository.createExpense/updateExpense`, atomically writes root, splits, local audit and a durable `LEDGER_CREATE_EXPENSE`/`LEDGER_UPDATE_EXPENSE` operation; worker sends authenticated `/v2/trips/:id/expenses` mutations with idempotency and base revision (`src/features/ledger/LedgerExpenseEntryScreen.tsx`, `src/data/repositories/ledgerExpenseRepository.ts`, `src/data/sync/ledgerExpenseSyncWorker.ts`). Offline save survives restart; server canonical response/pull reconciles the same Expense identity.
- Edit is a _revisioned correction_, not immutable root columns: repository `replaceExpenseData` updates original Money, and audit events/financial-core changed groups preserve revision history. Existing finalized-settlement guards and Stage 4C conflict handling constrain competing financial edits (`src/domain/ledger/conflict.ts`, `supabase/migrations/20260912000200_ledger_2_stage_4b_mutations.sql`, `20260912000300_ledger_2_stage_4c_conflicts.sql`). Do not describe original Money as unchangeable across a correction.
- Picker selection itself never writes. It also clears `draft.amount`, so merely switching the currency cannot save the previous number; a new amount must be entered. This prevents accidental implicit conversion, but conflicts with the proposed “change currency without changing the numeric amount” interaction. `EXACT` split draft inputs are not automatically converted; save remains subject to split reconciliation.

## 4. Exchange rates and Stage 5

- SQLite migration 9: mutable `ledger_rate_quotes` keyed by Journey/pair with `decimal_rate`, `effective_date`, `observed_at`, provider/reference and expiry; per-Expense `ledger_exchange_rate_snapshots` includes revision, manual reason, staleness state and supersession. Dev `ledger_rate_quotes` and `exchange_rate_snapshots` mirror the concepts (`supabase/migrations/20260912000400_ledger_2_stage_5_1_financial_evidence.sql`). Legacy `journey_exchange_rates`/`ledger_exchange_rates` in canonical baseline are **not** the Ledger 2.0 client-writable source (`docs/ledger/LEDGER_2_0_DOMAIN_MODEL.md`).
- Direction is **one original/quote currency unit → decimalRate settlement/base currency units**, not its inverse: `previewValuation` requires `quoteCurrency === original.currency` and `baseCurrency === settlementCurrency`, then `convertMoney` multiplies with exact decimal/rounding (`src/domain/ledger/valuation.ts`, `money.ts`). `SAME_CURRENCY` is exactly 1 by identity only, not a missing-rate fallback. Watch terminology: “base” in a rate pair is the destination, while Journey base is the settlement unit.
- Backend `GET /v2/trips/:id/ledger/rate-quotes` reads service-role-managed candidates; bootstrap/change feed caches them locally. Quote refresh is not a financial mutation. `backend/src/rateQuoteProvider.ts` defines and validates a provider interface, but the production code search found no caller, scheduled fetch, market-provider configuration, or ordinary Mobile write endpoint. Market retrieval/refresh and manual _quote-cache_ administration are therefore not delivered. The Exchange Rates route says “Not available in this build.” Dev fixture/import rates are not evidence of a live provider.
- `REFERENCE_RATE` consumes a trusted matching quote; `MANUAL_AGREED` consumes a positive explicit decimal and required reason; `ACTUAL_PAYER_COST` consumes non-superseded posted Money in settlement currency; `SAME_CURRENCY` requires exact match. The explicit `applyValuation` repository command creates rate/valuation snapshot, reallocates settlement splits, local audit and queued `LEDGER_APPLY_VALUATION`; Backend checks preview/base revision and calls `ledger_apply_valuation_5_1`. The normal UI does **not** call it (only the Stage 5.1 acceptance hook and worker use it). Stale quote acceptance requires a reason server-side. Cached matching quote does not automatically value an Expense.
- Accepted snapshot provenance includes date/source/observation/provider reference/manual reason/staleness/supersedes. A gap remains in ordinary read/explanation: `readExpenses` selects the **active valuation** and rate-snapshot ID, not full `exchange_rate_snapshots` history; local reconciliation stores valuation data but does not hydrate the complete rate evidence for the detail screen (`backend/src/supabaseGateway.ts`, `src/data/repositories/ledgerExpenseRepository.ts`). History/audit is in Dev, yet a user cannot inspect all provenance through the current normal UI.

## 5. Valuation

Accepted group value is a separately stored, versioned `settlement_valuation_snapshots` record with original and settlement Money, policy, rate/payment evidence reference, decimal, rounding and supersession. Active projection is singular; historical accepted snapshots and settlement inputs must remain frozen. Conversion uses original minor units and explicit scale, not floating-point JS rate arithmetic (`src/domain/ledger/money.ts`; migration 5/9; Dev `settlement_valuation_snapshots`). New same-currency Expenses receive `SAME_CURRENCY`; cross-currency forms save `RATE_REQUIRED`, null valuation and null settlement splits. A correction that changes original Money invalidates the old active valuation; unchanged Money preserves it (`LedgerExpenseEntryScreen.tsx` Save). The chosen quote carries an effective date, but there is no normal historical-date quote selection or automated revaluation on changed currency/base. Missing rates explicitly exclude Expense from authoritative converted totals and settlement readiness, without blocking local/remote Expense persistence. Display preference never revalues it.

## 6–7. Payments versus actual currency exchange

Expense PaymentRecord stores separate authorization, posted, fee Money/currencies, `postedAt`, optional bank FX evidence and supersession. It records what the payer actually paid, which can differ from original merchant price and agreed group valuation; merely adding evidence does not update valuation. `ACTUAL_PAYER_COST` explicitly selects an eligible posted record. A merchant/posted pair may imply an _observed effective ratio_, but no canonical “derived FX rate” is automatically promoted to a trusted market quote or accepted valuation. Review Evidence rule compares same-currency posted versus merchant amount only (`src/domain/ledger/reviewV2.ts`).

Stage 7 transfer repayment is a different Payment: `settlement_payments.payment_currency` may differ from frozen settlement currency; an immutable `repayment_valuation_snapshots` rate/source/reason and recipient-confirmed discharge record make its cross-currency effect explicit (`src/features/ledger/TransferDetailScreen.tsx`, `ledgerSettlementRepository.ts`, `supabase/migrations/20260912000900_ledger_2_stage_7_2a_payments.sql`). That screen has a **manual three-letter TextInput**, not the shared Currency Picker. Search filters also use their own currency selection control. Neither is a merchant Expense currency edit.

No canonical first-class cash/bank **exchange transaction** with two legs (e.g. NZD 500 → ISK 41,000), accounts, fees, actor, time and source was found in Ledger 2.0 schema, API, repository or UI. Rate snapshots and repayment valuation do not record that transaction. This is additional product scope, not a prerequisite for repairing Expense currency selection; seek product confirmation before adding it.

## 10–11. Offline, sync, conflict and audit

| Scenario                             | Observed design/result                                                                                                                                                                                                                                                                                                                                                           |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Transaction currency changes offline | Draft selection is volatile until Save. Valid Save commits revised original/splits, active valuation or `RATE_REQUIRED`, append-only local audit and owned durable operation in one transaction; restarts retain it. Reconnection sends operation with idempotency/base revision; concurrent financial edits conflict, not silent LWW. Remote authorization/validation can fail. |
| Journey base changes offline         | No command/path: impossible today. A direct mutation of `ledger_journeys` would be overwritten by bootstrap and violate lineage; do not treat personal `default_currency` as a surrogate.                                                                                                                                                                                        |
| Matching rate cached                 | Quote is available in SQLite after bootstrap/pull, but regular entry does not select/apply it; existing accepted valuation stays fixed. Only explicit Stage 5 valuation command can consume it.                                                                                                                                                                                  |
| Rate missing                         | Cross-currency Expense is stored/synced as `RATE_REQUIRED` with null converted splits; it remains visible, excluded from authoritative totals and blocks included settlement readiness. No 1:1 assumption.                                                                                                                                                                       |
| Connectivity returns                 | Existing Expense operations retry/reconcile, pull delivers server facts and quote candidates; **no automatic** completion of missing valuation or retroactive base conversion. Personal preference remains device/account-local.                                                                                                                                                 |

Stage 4B edit/delete/restore use revisioned operations and soft tombstones; Stage 4C treats original Money, splits and valuation as financially material conflicts and correction requests. Stage 5 valuation and PaymentRecord evidence are independent idempotent operations with separate audit; rate-candidate refresh is read-only to financial truth. Review findings are derived from canonical revisions, while personal decisions do not change Money. For a future Journey-base command, existing Expense-only queue semantics and idempotency are insufficient: it needs its own authorization, base settings revision, preview, durable local intent, conflict policy, audit/change-feed, and explicit treatment of open/finalized settlements; no current implementation supplies this.

## Decision and implementation dependency order

1. **KEEP:** original/posted/group/repayment Money separation; integer minor units and explicit ISO scales; immutable accepted rate/valuation/settlement evidence; `RATE_REQUIRED`; local-first queue and conflict/audit; account-scoped preference; Review as non-mutating observation.
2. **REPAIR:** Expense currency UX (explicit “correct original currency,” preserve numeric entry if approved, reset incompatible exact splits/valuation with explanation); clarify Settings label; connect an authorized valuation completion flow to existing quote/manual/posted-cost commands; expose provenance and safe rate-date/staleness handling. Do not silently revalue existing accepted facts.
3. **ADD only with approval:** Journey settlement-currency change as dedicated previewed, revisioned, audited command, including policy for existing accepted Expenses/open or finalized settlements and revaluation or migration _without rewriting original Money_; optional provider ingestion and preferred-currency read-only conversion with explicit provenance; actual currency-exchange transaction only if independently requested.
4. **REMOVE/RENAME ambiguity:** rename UI “Default Currency” to “Personal display currency (future conversion)” or “Preferred currency” after product decision; retain/migrate `account_local_state.default_currency` data. Treat migration-18 `ledger_preferences.default_currency` as legacy local residue, not a second source; retire only via a safe forward migration. Distinguish `settlement_currency` from rate pair `base_currency` and legacy `journey_ledgers.display_currency`.
5. **Exact shared-Picker persistence gaps:** `LedgerExpenseEntryScreen.tsx:636` selection itself is draft-only and clears amount; `app/(tabs)/expenses/settings.tsx:133` persists locally but never syncs nor changes valuation/display totals. Neither changes Journey base. See matrix above.
6. **Canonical model proposal:** retain `Expense.original Money` + revision; `JourneyLedgerSettings.settlement Money unit` + settings revision; per-user local `preferredDisplayCurrency`; mutable provider `RateQuote` cache; immutable per-Expense `ExchangeRateSnapshot` + `SettlementValuationSnapshot` with policy, original/settlement Money, effective date/source/freshness/supersession; separate PaymentRecord and frozen repayment/settlement facts. A preferred-currency report conversion is a labelled derived projection, never another Expense. Do not collapse posted payer cost into market FX or infer merchant Exchange transactions.
7. **Phases:** (i) approve exact terminology and correction UX; (ii) repair picker/save tests with existing schema/operations; (iii) expose existing Stage 5 valuation/provenance and offline missing/cached paths; (iv) approve Journey-base transition policy and implement settings command end-to-end, only after historical/settlement guard design; (v) optional provider and display-only converted reporting, then separately scoped exchange transactions if desired. Each phase verifies SQLite → queue → Backend → Dev → pull → reporting/Review.
8. **SQLite migration required?** **No** for Expense picker correction, existing valuation flow, or renaming UI; perhaps **yes** for a safely versioned local Journey settings mutation, pending state/change feed/provenance projection or retiring duplicate preference field. Decide after policy/contract; do not add a new Expense currency column.
9. **Backend/Supabase migration required?** **No** for existing Expense/valuation commands or picker wiring. **Likely yes** for Journey-base command/atomic revision+audit+change-feed and possibly rich historical provenance projection; provider integration may be service code without schema change because quote tables exist. Verify Dev schema/permissions in a dedicated implementation gate.
10. **Production migration risk:** no Production inspection or change in this audit. Legacy Ledger and Ledger 2.0 are separate. Historic rates, original/settlement values, finalized settlements and provenance cannot be bulk rewritten based on a display preference; any Production plan needs separately approved lineage mapping, backup/rollback, compatibility and financial reconciliation.
11. **Automated + physical acceptance:** unit-test zero/2/3-decimal currency correction without numeric conversion, invalid ISO, exact-split reset, identity 1 versus missing quote, inverse pair rejection, effective-date/stale/manual provenance and rounding; repository restart/offline queue/idempotent retry/conflict/deletion-restore; Backend/Dev authorization and snapshot/audit lineage; reporting buckets/Mine/Group/Review generations and frozen settlement/export before/after correction. On signed Simulator and physical device, select currency in new/edit then Save, force-quit offline, reconnect across two accounts/devices, inspect original/settlement/posted amounts and pending status, test missing/cached rate and conflict, confirm per-account preference survives restart but does not masquerade as Journey base. Journey-base device acceptance waits for a separately approved command/policy. Do not uninstall or clear real device data for this audit.
