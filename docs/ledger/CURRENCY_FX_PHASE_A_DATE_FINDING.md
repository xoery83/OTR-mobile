# Phase A `occurred_at` / economic-date finding

Date: 2026-09-17. Static lineage inspection only; no database, device or Production access. This is the **stop gate before Phase B**.

## Trace

1. New Expense form initializes `draft.date` from the phone's local `dateKey(new Date())`; the native date picker returns a `Date`, formatted with the **device-local** year/month/day (`src/features/ledger/LedgerExpenseEntryScreen.tsx:808–825,755–764,866–874`). Editing shows the **first ten characters** of persisted `existing.occurredAt`, without timezone conversion. OCR suggestion may supply its own `occurredAt` string. Neither Journey timezone nor a separate economic date is stored here.
2. Save emits `occurredAt = existing.occurredAt` only if the selected date equals the first ten characters; otherwise it sends **`YYYY-MM-DD`**, including every new manual Expense (`LedgerExpenseEntryScreen.tsx:380–383`). SQLite `ledger_expenses.occurred_at TEXT NOT NULL` stores the string unchanged; repository audit and operation snapshot/payload copy it (`src/data/db/migrations.ts` migration 5; `src/data/repositories/ledgerExpenseRepository.ts`). The local date-only string can thus survive offline restart.
3. The operation worker passes `expense.occurredAt` to `/v2` (`src/data/sync/ledgerExpenseSyncWorker.ts:382`). The request schema accepts any `z.string()` whose `Date.parse` succeeds, including both date-only and timezone-bearing timestamps (`src/data/api/ledgerMutationContracts.ts:63`). Backend composes the same string into the canonical response (`backend/src/supabaseGateway.ts:1296,1443`).
4. Dev `expenses.occurred_at` is **`timestamptz`**. Stage 4A and 4B RPCs cast the input string `::timestamptz` (`supabase/migrations/20260912000100_ledger_2_stage_4a_create.sql:17`, `20260912000200_ledger_2_stage_4b_mutations.sql:105`). The date-only input is resolved using the database session timezone; no Journey-local timezone is in the command or recorded with the timestamp. Backend read emits `String(row.occurred_at)` (`backend/src/supabaseGateway.ts:3551`); Mobile bootstrap/pull persists this returned string into SQLite (`src/data/repositories/ledgerReadRepository.ts`). Server reconciliation can replace the local date-only representation with a timestamp.
5. Historical data has multiple origins: Stage 9 import maps legacy `expenseDate` to `YYYY-MM-DDT00:00:00.000Z` (`backend/src/stage9Import.ts:1011`); UI fixture uses UTC timestamps (`backend/src/uiPolishFixture.ts:362`); other API clients can supply any parseable offset timestamp. An imported UTC midnight is a mapping convention, **not proof of the Journey's local midnight**. Ledger Journeys have dates, but no reliable timezone field in this path.

## Verdict: NO, not unambiguously for all existing records

For a just-entered date-only local draft, the user's selected calendar label is known **before** remote normalization. For all already-synchronized and historical records, `occurred_at` alone cannot prove which Journey-local calendar day the user intended. E.g. `2026-07-15T00:30:00Z` is July 15 in UTC/NZ but July 14 in some western timezones; a `timestamptz` retains an instant, not its original input timezone or calendar-date intent. Taking `slice(0,10)` after a round trip, or converting through the phone timezone, can silently choose a different date. Database session timezone is not a substitute for Journey timezone. Current Stage 5 quote validation checks currency pair but not Expense economic date. Therefore **Phase B must decide/add an explicit canonical `economic_date` (date-only) in the Mobile/Backend/Dev contract and migration before historical-rate lookup**, with a migration/backfill policy for ambiguous historical rows. Preserve `occurred_at` as occurrence timestamp where available; do not manufacture historic dates from UTC without provenance/explicit review. A legacy import date with documented source date may be recoverable case-by-case. Phase A makes no speculative schema migration.

## Safe Phase A invalidation boundary

If the edited draft's date label differs from `existing.occurredAt.slice(0,10)`, the **stored represented day certainly changes**: invalidate the existing active FX valuation, keep historical evidence, and use `RATE_REQUIRED` for cross-currency. If the labels match, this does **not** prove the true Journey-local day is correct; do not claim historical-rate eligibility from it or auto-revalue. Same-currency `SAME_CURRENCY` identity may be rebuilt. Expense date edits remain possible offline without provider access; finalized settlement guards still apply. Add regression tests for this conservative comparison and for the fact that no amount/currency-preserving edit may keep a valuation after a provable date-label change. Do not convert timestamp to UTC or the device timezone to decide the FX date in Phase A.

## Phase B decision gate

Specify a canonical `economic_date DATE`/`YYYY-MM-DD` independent of timestamp and timezone; require it in new Expense commands and include it in revision/audit, queue, bootstrap/pull, rate request key and Backend authoritative validation. Define how Journey-local calendar selection and OCR/import map to it, and a safely staged/backward-compatible migration for old clients. For old Expenses: source-proven date only when proven; otherwise mark unknown/review required, preserve prior accepted valuations and settlement history, and never silently backfill the day from a UTC timestamp. Do not start provider integration until this contract and backfill policy are approved and tested.
