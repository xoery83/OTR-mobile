# Currency / FX Phase C — automatic reference valuation

Date: 2026-09-17. Scope: approved ECB historical rates as default **reference estimates** for eligible cross-currency Expenses. They are not card/bank conversion, executable FX, cash exchange or proof of payer cost. MANUAL_AGREED, ACTUAL_PAYER_COST, SAME_CURRENCY and imported evidence remain separate policies. No Phase D/E/F or Production action.

## Trigger and precedence

The Backend periodically scans canonical `RATE_REQUIRED` Expenses after the B2 demand/candidate pass. A known explicit `economic_date`, active Expense, cross-currency pair, current Journey `REFERENCE_RATE` policy, fresh trusted B2 candidate, no active valuation, unresolved conflict or finalized settlement input, linked creator/owner authority and matching revision are required. The existing Stage 5 command creates the immutable ExchangeRateSnapshot, SettlementValuationSnapshot, settlement splits and financial audit/revision. A screen need not be open. Offline Expense creation remains local-first and is pushed by the existing queue before the Backend can value it. Candidate absence leaves `RATE_REQUIRED`; missing economic date leaves `ECONOMIC_DATE_REQUIRED`; same currency uses identity and never requests external FX.

The candidate cache is mutable, but an accepted snapshot is not. Re-running the scanner, restarting the app, provider correction and a newer quote do not revalue ACCEPTED Expenses. A financial correction can invalidate the active snapshot using Phase A/B1 semantics, retain the old evidence and form a new RATE_REQUIRED demand for the corrected amount/currency/date. Semantic automatic failures stop for that revision; transient failures retry after five minutes and concurrent revision/settings changes after one minute. Duplicate triggers use the same idempotency key and the Stage 5 revision lock.

## Server boundary and provenance

Dev migration `20260917000500` restricts service-role Stage 5 entry to `ledger_apply_valuation_c`. In one transaction it locks the Expense/settings/quote and checks request date = canonical Expense date = candidate request date; candidate reference date ≤ economic date and at most seven calendar days earlier; original→current Journey direction, settings revision for automation, ECB policy/source, pinned delivery URL, decimal and expiry. It rejects a forged Mobile quote or stale edit independently of local checks. Stage 5 remains the sole financial writer and rechecks revision, preview, authorization and finalized input protection.

Accepted reference evidence freezes both dates, rate, currency direction, ECB source URL, Frankfurter delivery URL, observation time, acceptance time, rounding mode, automation flag and supersession lineage. Backend/Mobile read models expose this as `referenceEvidence` alongside the policy. The source is the European Central Bank; Frankfurter is only the delivery adapter. User-facing Phase E detail presentation is deferred. Migration 005 adds a revision-keyed automatic failure table; SQLite v24 adds only the read-cache field for accepted provenance.

Reporting uses accepted Stage 5 splits, so a RATE_REQUIRED Expense enters converted Mine/Group/Categories/Analysis only after the canonical acceptance, without optimistic double count. Existing Review 2.0 re-evaluation runs after acceptance. Settlement readiness uses the canonical accepted valuation, while existing open/finalized settlement guards remain in force. This phase does not alter their calculation engines.
