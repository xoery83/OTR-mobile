# Spending Analysis 当前功能说明（展示层重设计讨论用）

核对日期：2026-09-29

代码基线：`8cbfc82`

用途：给 GPT / 设计讨论提供当前实现的事实依据。本文不是新的产品方案，也不批准新增功能。

## 1. 一句话概括

**Spending Analysis 是当前单个行程的支出分组浏览器：选择看谁的消费、按什么维度分组、看哪段时间，再点击某组查看构成它的费用。**

当前正式页面采用列表展示，每行有分组名称、费用数量和金额。截图对应此正式实现。

它分析的是消费归属与费用分布，不是成员欠款、结算转账或还款进度。消费分摊金额与付款金额是两个不同概念。

## 2. 入口与分析上下文

- 入口：Ledger 的 Spending 页面 → `See analysis`。
- 进入时继承当前行程、Mine / Group，以及 Group 下已经选中的成员。
- 默认维度：`Category`；默认时间范围：不限制日期。
- 分析始终限定在一个行程内，不是跨行程的 My Ledger 报表。
- 页面本身没有行程切换器、币种切换器，也没有单独展示行程名称的内容区。

可以把当前分析状态理解为：

> 行程 × 个人/全组/指定成员 × 分析维度 × 日期范围

### 三种实际观看口径

| 界面选择       | 分析对象                     | 金额口径                                                                        |
| -------------- | ---------------------------- | ------------------------------------------------------------------------------- |
| Mine           | 当前账号在此行程中关联的成员 | 此成员在每笔费用中保存的分摊金额                                                |
| Group → Group  | 整个行程                     | Category / Time / Payer / Currency 使用费用全额；Participant 使用各成员分摊金额 |
| Group → 某成员 | 指定成员                     | 与 Mine 相同的个人分摊算法，只是成员换成所选对象                                |

**Mine 不等于“我付款的费用”。** 只要费用中有我的有效分摊金额，即使别人付款，也会计入我的消费；我替别人付款的部分不会全部变成我的消费。

Group 下有第二排可横向滚动的成员选择：

- 第一个选项是全组 `Group`，后面是行程成员。
- 按全行程的有效个人消费金额从高到低排列；金额相同按名字排列。
- 零消费成员仍可选择；排序不会随着 Analysis 日期范围改变。
- 成员按钮显示姓名的第一个空格分隔部分；辅助功能标签保留全名。
- 选中某成员后，说明文字显示全名；维度、日期切换和下钻会继续携带该成员。
- 切换到 Mine 会清除所选成员，因此随后再切回 Group 是全组口径。

## 3. 五个已实现的分析维度

维度按钮横向滚动。截图右边没有完整出现的第五项是 `Currency`。

| 维度        | 分组依据                   | 全组金额                   | Mine / 指定成员金额                      | 排序         |
| ----------- | -------------------------- | -------------------------- | ---------------------------------------- | ------------ |
| Category    | 费用分类                   | 该分类的费用全额合计       | 该分类中此成员的分摊合计                 | 金额从高到低 |
| Time        | 费用记录日期，按天         | 当天费用全额合计           | 当天此成员的分摊合计                     | 日期从早到晚 |
| Payer       | 费用的付款人               | 该付款人支付的费用全额合计 | 由该付款人支付、但分摊给此成员的金额合计 | 金额从高到低 |
| Participant | 费用参与成员及其保存的分摊 | 每个成员的消费分摊合计     | 只显示此成员自己的分摊合计               | 金额从高到低 |
| Currency    | 费用的原始币种             | 该原币种费用的折算全额合计 | 该原币种费用中此成员的折算分摊合计       | 金额从高到低 |

除 Time 外，金额相同时按分组标签排序。没有手动排序、Time 的金额排序、周/月聚合或补齐无消费日期的功能。

### 最容易误解的两个维度

**Payer 和 Participant：**

假设一笔晚餐，折算后为 NZ$100，Alex 付款，Alex 分摊 NZ$60，Bea 分摊 NZ$40：

| 当前视图                     | 结果                    |
| ---------------------------- | ----------------------- |
| Group → Payer                | Alex：NZ$100            |
| Group → Participant          | Alex：NZ$60；Bea：NZ$40 |
| Bea 的个人视图 → Payer       | Alex：NZ$40             |
| Bea 的个人视图 → Participant | Bea：NZ$40              |

所以，个人视图中的 Payer 回答的是“我的消费由谁付款”，不能直接标成“这些人各付了多少”。个人视图中的 Participant 通常只有自己一组，也不是同行成员对比。

**Currency：**

分组名称可以是 EUR、USD、NZD，但各组金额都显示为当前行程的结算币种。例如 `EUR — NZ$200` 表示“原币种为 EUR 的费用，按保存的有效估值折算后合计 NZ$200”，不表示 €200。

### 每行的费用数量

- 是此分组包含的不同 Expense 数量，不是交易人数，也不是分摊条数。
- 同一 Expense 在同一分组内只计一次。
- Group → Participant 中，一笔多人费用会出现在多个成员的组内，所以各成员的费用数量不能相加当成行程费用总数。
- 各成员的金额使用各自分摊，不会给每个人重复记整笔费用。

## 4. 哪些费用进入分析

正式页面通过 Repository 从当前账号可访问的 SQLite 缓存中计算；打开分析和切换维度不直接请求远程分析接口。

当前进入金额与分组的主要条件：

1. 属于当前行程，且当前账号有此行程的本地访问上下文。
2. 记录已同步，或者是当前账号自己的本地记录。
3. 没有被删除。
4. 业务状态是 `ACCEPTED`。
5. 有当前有效的估值快照和所需金额；个人口径还需要此成员的分摊金额。
6. 没有未解决的 Expense 冲突。
7. 不是已经被确认纠正链替代的旧来源 Expense，避免旧费用和后继费用重复进入当前统计。
8. 满足当前日期范围。

需要特别保留的语义：

- **不参与组内结算的费用仍进入支出分析。** `EXCLUDED` 只影响谁欠谁，不会抹掉消费。
- 缺少有效估值、`RATE_REQUIRED`、草稿、已删除费用、未解决冲突不进入当前分组金额。
- 不要求费用已经完成云端同步。符合条件的当前账号本地有效费用可以计入。
- 不在页面临时用最新汇率重算；使用保存的当前有效估值与分摊金额。
- 金额以整数最小货币单位累计，按行程币种及精度格式化显示。

### 与 Spending 首页的金额关系

当前 Spending 首页的展示总额可以加上带 `≈` 的估算金额；**Analysis 只取已接受的有效金额，不纳入展示估算**。

因此，有尚未接受的估算费用时，首页展示总额可能大于 Analysis 的分组合计。这是当前两个页面使用的口径差异，不应在重设计时默认它们必然相等。

Analysis 没有额外展示“多少笔未估值 / 多少笔冲突 / 多少笔被排除”的解释区。分组结果中的未估值和冲突计数固定为 0，不能用这些字段直接生成全行程排除提示。

## 5. 日期范围

右上角 `Range` 打开 iOS 原生选择菜单，目前有以下五项：

| 选项         | 实际行为                                                   |
| ------------ | ---------------------------------------------------------- |
| All trip     | 不设日期条件，包含当前行程中所有日期的合格费用；这是默认值 |
| Today        | 今天                                                       |
| Yesterday    | 昨天                                                       |
| This Trip    | 使用行程的开始日到结束日，含首尾两天                       |
| Last 30 days | 今天及之前 29 天                                           |

**All trip 与 This Trip 并不完全相同。** 前者只限定行程，不限定日期；后者严格限定行程日期区间，行程前后记录的费用可能被排除。

- 行程缺少开始或结束日期时，选择 This Trip 不会应用新范围，当前没有额外解释提示。
- Analysis 自己没有指定日期或自定义日期区间输入；下钻后的 Search 筛选页具备这些能力。
- 页面显示实际日期 / 日期区间，而不是一直显示预设名称。
- 底层范围为 `[from, to)`：开始包含，结束不包含；结束通常是所选最后一天的次日零点。
- Time 分组取 `occurred_at` 字符串的前 10 位，日期筛选使用该字段。它没有直接按独立 `economic_date` 列分组，也没有按旅途所在地时区转换。
- Today / Yesterday 先按设备本地日期确定是哪一天，再构造 UTC 零点边界。这是现有代码行为；若重设计要求按当地时刻统计，应另行检查日期契约，不能仅改文案。

## 6. 点击分组后的完整行为

路径：

> 分析分组 → 共用 Search 费用结果页 → 单笔 Expense 详情 → 返回

点击后携带行程、观看对象、当前范围、分组条件和来源标签：

| 点击对象 | 传给结果页的筛选                                                   |
| -------- | ------------------------------------------------------------------ |
| 分类     | 精确分类                                                           |
| 某天     | 该日 UTC 零点到次日零点，替换当前的大范围日期条件                  |
| 付款人   | 精确付款人成员 ID                                                  |
| 参与成员 | 精确参与成员 ID；全组 Participant 下钻同时切为该成员的个人金额口径 |
| 币种     | 精确原始币种                                                       |

同时开启 `authoritativeOnly`，以合格有效费用为结果来源，而不是混入普通 Search 中可见的未估值或冲突记录。

结果页当前提供：

- Mine / Group / 所选成员全名，以及分组来源标签。
- 匹配费用数量、纳入总额的数量，以及此结果集的汇总金额。
- 搜索文字、可调整的筛选、已应用条件标签及移除条件。
- 每页 50 条的分页费用列表，默认日期从新到旧。
- 点击费用进入正式 Expense 详情。
- 普通 push / back 保留 Analysis 的维度、日期、观看对象和滚动状态。

**金额展示有一个必须理解的差异：** Search 顶部汇总使用当前分析口径和行程结算币种，但每条费用右侧显示的是“该费用的原币全额”。在个人视图下，这个行金额也不是自己的分摊金额。因此，把明细行右侧金额相加，不一定得到上方分析金额。

用户在 Search 内修改筛选后，看到的是新的结果集；这些调整不会反向修改 Analysis 的筛选状态。

## 7. 当前展示与页面状态

### 已有展示

- 顶部标题 `Spending Analysis`、返回按钮、Range 按钮。
- Mine / Group 分段选择。
- Group 下的全组 / 成员横向选择。
- Category / Time / Payer / Participant / Currency 横向选择。
- 当前成员与日期范围说明，以及“每组可打开对应费用”的提示。
- 白色列表，每行显示名称、`1 Expense` / `N Expenses`、金额。
- 更新时显示加载指示与 `Updating analysis…`。
- 请求成功时把控制状态与结果一起切换；旧异步请求不会覆盖新结果。
- 请求失败保留上一次成功视图，显示可点击重试的错误文字。
- 空态：`No Expenses with a confirmed exchange value for this view.`
- 分组行提供名称、金额、数量的辅助功能标签；极大字体下行内容改为上下排列。

### 正式页面当前没有

- 顶部总消费卡片、总笔数汇总。
- 百分比、进度条、环图、饼图、柱状图、折线图。
- 每日累计、平均每日支出、趋势对比、预算或超支提示。
- 多维交叉分析、多个维度同时展示、周 / 月切换。
- 单独的分析分享 / 导出按钮。
- 固定在顶部的维度控件；当前控件与列表一起滚动。
- 页面自身的下拉刷新或离线 / 数据新鲜度标识。

这些是正式页面当前未提供的能力，不代表其他 Ledger 页面或后端完全没有相邻能力。

## 8. 重设计前应知道的限制

以下是代码阅读发现的实现行为或边界；不是本次新增修复，也不全部代表已在设备上重现的问题。

| 项目                   | 当前情况                                                             | 对设计讨论的影响                                                                           |
| ---------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 总额口径               | Analysis 不包含展示估算，Spending 首页可以包含                       | 总额卡片、标题和范围说明需要让用户理解金额来源                                             |
| Payer 命名             | 个人口径中是按付款人归组的“个人分摊”                                 | 不能套用全组“付款金额”的文案                                                               |
| Participant 在个人视图 | 只分析此成员自己                                                     | 通常只有一组，不能假设是同行对比                                                           |
| Currency 命名          | 原币种分组，行程币种金额                                             | 原币标识与金额币种需要同时清楚                                                             |
| 零分摊费用             | Analysis 可把 0 分摊记录计入组内数量；Mine 明细列表会隐藏 0 分摊记录 | 分组笔数与下钻结果笔数可能不一致，金额通常不受影响；现有一般下钻一致性测试没有覆盖这一组合 |
| 明细金额               | 每行是原币全额，上方汇总可能是个人折算金额                           | 需要区分“整笔费用”“个人消费”“原币”“折算币”                                                 |
| 数据刷新               | Analysis 主要在进入和操作控件时查询；没有 focus 刷新或数据库订阅     | 从详情返回后可能仍保留旧分组；成员元数据在页面内缓存，普通重查不会更新成员排序来源         |
| 空态文案               | 统一说明没有已确认换算价值的费用                                     | 不能区分没有费用、日期内没有费用、全是冲突或缺估值                                         |
| 大列表                 | Analysis 用 ScrollView 一次渲染全部组；下钻费用页才有虚拟列表和分页  | 分类较少时简单；天数或组数很多时需要另行评估                                               |
